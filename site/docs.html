listCompanyJobs(input)

    
    
Every job a company currently has posted.

    

      

        
By name

        

      

      

        
By URL

        

      

      

        
By board

        

      

    

    

      Returns ListedJob[], shaped
      { id, title, location, url }. Throws
      UnresolvedCompanyError when no scraper can be resolved for
      the company. Object input also takes search and
      minJobs (see resolution).
    

  


  

    
      
fetchJob(input)

    
    
A single posting, with its full content.

    

      

        
By posting URL

        

      

      

        
Embedded board

        

      

      

        
By company + id

        

      

    

    

      Returns a Job: a ListedJob plus
      content, the full posting. content is whatever
      the board gives up: usually stringified JSON, sometimes markdown or plain
      text.
    

    

      A URL is only trusted for the job id it carries itself. Sniffing a careers
      page turns up plenty of job links, and the first one isn't the one you
      asked for, so fetchJob on a board's landing page raises
      rather than fetching an arbitrary posting.
    

  


  

    
Resolution, without fetching

    

    

      resolveCompany takes the same input as
      listCompanyJobs.
    

  


  

    
Scrapers directly

    

      Every board's scraper is exported under scrapers, and takes
      the board slug.
    

    

    

      Some boards (Ashby, Lever, Shopify) only hand over full postings through
      their list endpoint. You don't need to know which:
      getJobContent fetches the list itself when its cache is cold,
      so a job is always fetchable at will.
    

    

      This is also the better tool for bulk work.
      listCompanyJobs and fetchJob each build a
      scraper and dispose of it before returning, which drops whatever it cached
      (notably the job list some boards need to answer
      getJobContent from). Fine for one lookup; wasteful for many
      jobs from the same company, since each call re-fetches that list. Hold
      onto a scraper yourself instead:
    

    

  


  

    
Errors

    

      
UnresolvedCompanyError

      

        No scraper serves the company. Carries the input that
        failed, and blocked: whether the browser's CORS policy
        blocked any board along the way (so it may resolve from Node).
      

      
CorsError

      

        Browser only. A request was blocked (most likely by CORS) before any
        response arrived. Carries url.
      

      
HttpError

      

        A board answered non-2xx. Carries status,
        statusText and url. A stale job id surfaces as
        a 404 here rather than as job content.
      

      
JobNotFoundError

      

        The board served its list, but nothing in it has that id. Carries
        jobId and companySlug.
      

    

  






  
Guides


  

    
How a company gets resolved

    
Given a name or URL, in order:

    
    
      
  1. 
        URL match: every scraper gets asked whether it
        recognizes the host. A match yields the board slug and, on a posting
        URL, the job id.
      
    2. 
      
  2. 
        Domain lookup: the hostname is checked against the
        domains companies are known to post on. A company that's been seen on
        pinterestcareers.com once is found there forever after,
        without a single request.
      
    3. 
      
  3. 
        Registry lookup: the name is normalized ("Apollo.io, Inc."
        → apolloio) and checked against the known companies. A
        careers site names itself rather than the company, so
        pinterestcareers is also tried as pinterest.
      
    4. 
      
  4. 
        Page sniffing: if none of that lands, the page is
        fetched. Every link in its markup is run back through step 1, since a
        company's own careers page is bespoke but the board it embeds leaves its
        slug there
        (boards.greenhouse.io/embed/job_board/js?for=airbnb).
        Failing that, the page usually names its own company in
        og:site_name or JSON-LD, which goes back through step 3.
      
    5. 
      
  5. 
        Slug guessing: the multi-tenant boards are probed in
        parallel with slugs derived from the name (acmecorp,
        acme-corp, and per-board variants). A board's own tracking
        params (?gh_jid=) hint at which to try first. The first
        board with at least minJobs real postings (3 by default)
        wins, since a slug answering only proves the board exists, not that the
        company uses it, and plenty keep a forgotten trial account holding one
        "Test UAT" posting. Placeholders like that, and talent-community
        catch-alls, don't count.
      
    6. 
      
  6. 
        Web search: if a SerpApi key is configured, a
        site:-scoped search over the board domains. See
        Web search.
      
    7. 
      
  7. Otherwise, UnresolvedCompanyError.
    8. 
    

    

      Anything found in steps 5 and 6 is written to the registry, so the next
      lookup is a plain hit. So is the careers domain a company was found on,
      whichever step found it. That's what collapses the whole pipeline to step
      2 the second time around.
    

  


  

    
Web search (optional)

    

      Slug guessing only works when the slug looks like the company name. It
      doesn't for Workday, whose slugs are tenant.pod.site triples
      (autodesk.wd1.Ext) that can't be derived from anything. A
      SerpApi search finds those.
    

    

      

        
In code

        

      

      

        
Environment (Node only)

        

          
SERP_API_TOKEN=...  # or SERPAPI_KEY, or SERPAPI_API_KEY
SERPAPI_SEARCH_LIMIT=100
SERPAPI_SEARCH_PERIOD=month

        

        
Browsers have no environment, so they use the code form.

      

    

    

      

        
          

            Option
            Default
            
          

        
        
          

            apiKey
            env in Node, else null
            Search is skipped entirely when unset
          

          

            limit
            250
            Max searches per period
          

          

            period
            'month'
            'day' or 'month'
          

          

            resultCount
            10
            Results requested per search
          

          

            resultTtl
            30 days
            How long a search's results are reused
          

          

            batchSize
            5
            Companies per query in a batched search
          

        
      

    

    

      The defaults match SerpApi's free tier: 250 searches a month. Check your
      own dashboard, since the allowance changes. Usage is counted in
      search-usage.json (see state) and resets
      when the period rolls over; a search is counted before its response lands,
      since a request that errors mid-flight still spends quota. Once the limit
      is hit, search silently stops being attempted and resolution falls back to
      the earlier steps.
    

    
Keeping search cheap

    
    
      
  • 
        Results are remembered, in
        search-results.json, including fruitless ones: not finding
        a company is exactly the case that would otherwise re-search on every
        lookup. Reused for resultTtl, since companies change job
        boards rarely.
      
    • 
      
  • 
        Concurrent lookups of the same company share one search, so resolving a list in parallel can't double-spend.
      
    • 
      
  • 
        Bulk lookups are batched.
        searchForBoardsBatch(names) ORs
        batchSize companies into one query at
        num=100 and attributes results back by slug: a 5×
        reduction. Anything already remembered is skipped, so re-running a large
        list is nearly free.
      
    • 
      
  • Search is only reached when slug guessing has already failed.
    • 
    

    

    

      A search result is never trusted on its own. Searching for a company that
      other companies' job posts name-drop (an HR platform, say) returns boards
      belonging to entirely different companies, so a result is only accepted
      when the slug resembles the company name and the board
      clears the same minJobs bar as slug guessing. A board that a
      search finds but whose API won't serve it is treated as unresolvable,
      rather than registered as an entry that would always fail.
    

    

      Search is on whenever a key is configured. Turn it off for a single call
      with search: false:
    

    

  


  

    
The companies registry

    

      src/companies.seed.ts is the list the package ships with
      (exported as seedCompanies). Entries carry the board (scraper
      + slug) and, where known, the domains the
      company posts on: never a shared board host, which would point every
      company on that board at one entry. On first run it's copied into the data
      dir, which then becomes the live registry. Companies discovered at runtime
      are appended there, not to the seed.
    

    

      Each entry records where it came from (seed or
      discovered), and the file records the package version it was
      last reconciled against. On the common path that version matches and
      loading is just a parse. When it doesn't, because you upgraded, the two
      lists are merged (mergeRegistry(stored)):
    

    
    
      
  • 
        the shipped list wins for anything it covers, since a release may have
        corrected a slug
      
    • 
      
  • everything you discovered yourself is carried over untouched
    • 
      
  • 
        seed entries a release has dropped go away, since their
        removal was deliberate
      
    • 
    

    

      So upgrading never discards your discoveries, and never leaves you stuck
      on a stale shipped list. Read it with listCompanies(); add to
      it with registerCompany().
    

  


  

    
Where state lives

    

      

        
Node

        
Everything mutable lives in ~/.job-scraper:

        

          

            
              

                companies.json
                the registry
              

              

                cache/
                cached board responses
              

              

                search-results.json
                what web search turned up per company
              

              

                search-usage.json
                search quota accounting
              

            
          

        

        

          It's in your home directory rather than the working directory so every
          project on the machine shares it: a company should only need
          discovering once, and a board one project fetched shouldn't be
          re-fetched by the next. Writes are atomic (temp file then rename), so
          concurrent processes can't read a half-written registry. The paths are
          exported as dataDir, cacheDir and
          companiesFile.
        

        
    
          
  • Move it with JOB_SCRAPER_DATA_DIR.
    • 
          
  • Delete companies.json to reset back to the seed.
    • 
          
  • 
            Set DISABLE_COMPANY_REGISTRY to skip the stored file
            entirely (reads and writes) for the process, so the registry is
            always the seed, in memory only. Handy while changing its shape.
          
    • 
        

      

      

        
Browsers

        

          There's no filesystem: the registry and search state go to
          localStorage (falling back to memory), and board
          responses to the Cache API. dataDir,
          cacheDir and companiesFile are only Node
          paths; in browsers they're just the names the same state goes by. None
          of the environment variables apply.
        

      

    

  


  

    
Caching

    

      Every board request is cached, keyed by URL and request body. It's on by
      default, since scraping the same board twice in a session shouldn't cost
      two round trips, but the TTLs are the package's opinion, not yours:
    

    

      

        
In code

        

      

      

        
Environment (Node only)

        

          
JOB_SCRAPER_CACHE=off
JOB_SCRAPER_CACHE_TTL=3600000

        

        
Browsers have no environment, so they use the code form.

      

    

    

      

        
          

            Option
            Default
            
          

        
        
          

            enabled
            true
            
          

          

            ttl
            null
            
              Milliseconds. null keeps each scraper's own choice (a
              day, mostly)
            
          

          

            dir
            ~/.job-scraper/cache
            In browsers, the name of the Cache API cache
          

        
      

    

    

      Precedence is explicit override → environment → default.
      enabled can only turn caching off: scrapers
      opt out per call in some places (a discovery probe shouldn't be answered
      from cache), and config can't force those back on.
    

    

      In browsers, responses go to the Cache API with the same TTLs, and aren't
      cached at all where it's unavailable. Failed responses are never cached: a
      404 body must not become an entry a later call would trust as job content.

Running in browsers

    

      The same API runs in browsers through any bundler (the
      live demo above is the package itself), with a
      few differences:
    

    
    
      
  • 
        Only Ashby, Greenhouse, Lever, SmartRecruiters and Rippling allow
        cross-origin requests. A board that doesn't throws
        CorsError; when it was hit during resolution instead, the
        UnresolvedCompanyError has blocked set. Either
        way it works from Node, which doesn't enforce CORS.
      
    • 
      
  • 
        Configuration is configureCache and
        configureSearch only; environment variables are Node only.
      
    • 
      
  • 
        State goes to localStorage and the Cache API (see
        Where state lives), and the dataDir,
        cacheDir and companiesFile paths are Node
        only.
